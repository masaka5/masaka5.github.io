# 推流性能与稳定性验证

日期：2026-11-13。服务：本机 SRS 8.0.74，HTTP WHIP 1985、WHEP 1985、HTTP-FLV 8080。生产流 `live/livestream` 只观察；测试使用独立 `codex-stability-*` 流，未改服务配置。

## 已捕捉的故障

60 秒观察中，生产流视频帧计数始终停在 2815，音频帧从 5344 增至 8310，连接仍为 active。新增 WHEP 接收器处于 connected，却没有收到视频。这证明“连接还在”和总码率不能代表视频在传输。

旧版送帧完全依赖 requestAnimationFrame。真实 Edge 最小化窗口、去掉 Playwright 默认后台豁免参数后，8 秒内视频编码只增加 8 帧；恢复窗口后回到 30fps。不能直接读取用户正在推流的浏览器内部状态，因此不能断言生产流只有这一个原因。

## 本次改动

- 独立 Worker 时钟，仅在 rAF 停顿时接管；前台仍使用原 rAF。Worker 最多一个未处理通知，主线程繁忙时不堆积任务。
- 静态推流画面约 10fps 保活；未推流时仍按需渲染。
- 分开检查视频编码帧与视频发送字节，不允许音频掩盖视频停止。约 5 秒进入“画面停滞 · 恢复中”，触发重绘/送帧恢复；约 10 秒仍无进展则重连。
- 单次合成异常不会永久中断调度；错误通知限频。
- 停止推流、停止录制及关闭页面时回收时钟。原画推流与独立推流输出均覆盖。
- 减少合成热路径的数组和键值分配；保留 GPU 滤镜和浏览器原生硬件编码。

## 实测结果

| 测试 | 结果 |
| --- | --- |
| 最小化 8 秒，目标 30fps | 旧版编码 +8 帧；新版 +216 帧，约 27fps |
| 独立 SRS 流连续 300 秒 | 149 个样本，接收端解码 12607 帧；没有未解释的持续停滞 |
| SRS 动态阶段 | 1080p，发送帧率中位数 46fps；包含最小化窗口阶段 |
| 文本/倒计时场景 JS 合成 | 中位数约 0.1ms；编码约 5.37ms/帧 |
| 接收端 | 丢包 0、解码丢帧 0；HTTP-FLV 通过 FFmpeg 完整解码，退出码 0 |
| 停顿记录 | 2 次，总 5.649 秒：一次场景切换约 0.199 秒，一次主动停止视频轨道约 5.45 秒 |
| 故障注入 | 状态由 live → stalled → live；恢复回调触发后，测试夹具恢复轨道，继续解码；10 秒无进展重连另有单元测试 |
| JS 堆 | 约 2.14–3.04 MiB，在本次观察期间波动回收；不是整个浏览器/GPU内存 |
| Edge 光学时间戳回环，2K 场景+标题 | 实际发送 1920×1080/60fps；p50 73ms、p95 74ms、最大 75ms；合成约 2ms |
| 自动化核心 | 51 项通过，覆盖静态保活、时钟背压、音频掩盖视频停止、渲染异常、兼容降级、重连和清理 |

首轮 120 秒测试发现 2fps 静态保活会产生多次播放器 freeze 统计，因此最终提高为约 10fps。不能将当前结果写成“零冻结”。

## JS 与 WASM 的结论

部署路径没有自定义 WASM 编码器。此次主要瓶颈为浏览器调度和数据流健康判断，WASM 不能阻止 rAF 后台暂停，也不能替代 ICE/拥塞控制。像素处理保留 GPU，编码保留浏览器 WebRTC 原生实现。没有加入软件 WASM 编码或额外读回/内存拷贝，也不声称完成了 WASM 加速。

## 验证边界

300 秒是回归与短时稳定性验证，不代表全天运行保证。实际摄像头、捕获窗口、操作系统节能/休眠、浏览器冻结标签页、远端播放器缓存仍可影响结果。页面被操作系统完全挂起时，Worker 也无法运行；恢复后监控会继续。回环延迟不代表公网端到端延迟，也没有把 RTT 当作画面延迟。

证据：`broadcast-srs-observe.json`、`broadcast-srs-stability-final.json`、`broadcast-background-before.json`、`broadcast-background-final.json`、`broadcast-latency-stability-final.json`、`broadcast-stability-summary.json`。测试源码位于同一归档的 `_scratch/ops-tests/`。
