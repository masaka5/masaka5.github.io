# 推流低延迟优化

沿用静态浏览器架构；不增加服务，不改用户服务器配置。保持默认 2K/60 画布与本地录像参数。

- [x] 建立光学时间戳与 RTP 指标基线，分别记录画面时间差、渲染、编码、包队列、接收 jitter buffer。保留同条件基线代码。
- [x] 为 WHIP 增加隔离的实时发送策略：默认低延迟（发送最多 1080p、60 fps；按 CPU/网络压力自适应分辨率和码率）；原画模式保留完整输出。发送优先级、sendonly、H264/VP8 兼容优先、协商后重新设置参数；保持浏览器拥塞控制，不强制最低码率。
- [x] 新建纯策略与统计模块 low-latency.js：有限数值归一化、发送限制、报告增量、压力/恢复迟滞。真实统计 RTT、编码耗时、包队列、码率、限制原因；没有测量值显示为空，不能把 RTT 冒充端到端延迟。
- [x] GPU 中性效果快速路径；缓存 GPU 限制、缓冲与几何。独立 2D 发布画布处理普通来源、静态文字/倒计时；复杂滤镜、抠像与滚动字幕保持原 GPU 渲染。发布预览复用发布画布；本地原画录像独立保留。
- [x] RTMP 50 ms 分块，立即有序发出，ACK 窗口有界、时间和字节积压保护；不丢 WebM 中间块，压力过大重新连接。服务端收到媒体 ACK 后才显示已连接。
- [x] 实时模式选择保持紧凑；状态栏仅显示 RTT / 编码 / 队列必要指标，详细数据放 title。新配置刷新保留，无密钥持久化。
- [x] 测试先红再绿：策略边界、协商参数兼容回退、编码器负载/网络压力自动降级与恢复、慢 ACK 无串行堵塞、停止清理。真实 Chromium/Firefox/Edge 与 RTP、HTTP WHIP、录像、像素、布局回归。
- [ ] 同一基线比较；不宣称能控制外部服务器或播放器缓冲。仅部署运行文件，源包归档；线上实测确认。

测量：2026-11-13，本机浏览器回环、光学时间戳、接收端默认缓冲。旧版 2K/60 场景 p50 315ms / p95 393ms / 实际发送 12fps；新版实时模式 p50 50ms / p95 67ms / 实际发送 60fps。原版使用 VP8、新版优先 H264，发布画布上限为 1080p；浏览器带宽控制在短测试中还会调整实际编码分辨率，因此不属于等画质比较，也不能外推用户服务端延迟。720p30 p50 基本持平（67ms → 68ms）、p95 117ms → 85ms。Firefox 新版 2K 场景回环 p50 50ms / p95 51ms。重滤镜和同时 2K 录像开销仍较高（当前测试约 190–350ms），没有为了跑分禁用这些功能。网络慢 ACK 150ms 模拟可持续收到真实 WebM 数据；超 800ms 积压自动重新连接。生产不新增服务器。

Edge 对照：原版实际编码 1280×720 / 59fps，p50 53ms / p95 54ms；新版实际编码 1920×1080 / 59fps，p50 73ms / p95 75ms。硬件加速条件下原版已经很快，新版传输分辨率更高但延迟略增；不能将软件 Chromium 的提升倍数宣传为所有浏览器的提升。
